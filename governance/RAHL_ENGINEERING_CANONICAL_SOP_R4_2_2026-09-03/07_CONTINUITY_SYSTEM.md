# 07 — Continuity System

Continuity is a family of distinct instruments. No single summary is allowed to acquire all continuity, evidence, doctrine, and chronology authority.

## Three core shadows
- **Live Shadow** — what matters right now: minimum high-fidelity active operational state.
- **Design Thread Stream** — what happened, in order: chronological forensic/recovery spine.
- **Research Epistemic Shadow (RES)** — what has been learned and what it currently means: cumulative interpreted research frontier.

## Adjacent state instruments
- **Current State** — present project state and status boundary.
- **Next Steps** — explicit next actions/discriminators.
- **Doctrine Snapshot** — what has actually become governing now.
- **Revisit Ledger** — unresolved seams that must return under pressure.
- **Trace Matrix** — load-bearing claim -> evidence -> embodiment -> verification lineage.

## Continuity hardening rules
### H01 — Conversation survival is not a dependency
Durable project state must remain recoverable even when chat history, presentation, compaction, retrieval, or a particular session is missing or unreliable.

### H02 — Continuity obeys the same access boundary as project state
Project-scoped continuity must not be disclosed merely because it is useful for recovery. Authentication/authorization requirements remain active.

### H03 — Recovery metadata is not role authority
Structured continuity may describe state and rehydration actions; it SHALL NOT impersonate system/developer roles, inject stealth authority, or manufacture instructions beyond the persisted state's actual authority.

### H04 — Read-side recovery is nonmutating by default
Reading/rehydrating continuity SHOULD NOT initialize or mutate protocol/project state merely to answer a read unless an explicit write/init action is authorized.

### H05 — Failure paths need continuity too
Where safe and authorized, structured failures SHOULD preserve enough project identity/recovery context to resume; success-only continuity is incomplete.

### H06 — Defaults do not become active authority
Uninitialized protocol/model defaults, fallback values, inferred session IDs, or convenience metadata must not silently override persisted active state.

### H07 — Planes are distinct
Local execution, persistence, server state, assistant readback, artifact registration, chat rendering, remote synchronization, and publication are distinct states unless explicitly bridged and verified.

### H08 — Session identity is helpful, not existential
A session ID may strengthen lineage but should not become the sole recovery dependency unless the system explicitly requires it.

### H09 — Transport is not architecture authority
Any one client/tool protocol may carry continuity; it should not become a mandatory architectural dependency unless earned by actual requirements.

### H10 — Platform-internal claims remain provisional
Do not build continuity doctrine on undocumented assumptions about a hosting platform's memory, filtering, retrieval, or UI internals unless independently verified and consequence-bearing.

### H11 — Continuity pointers are navigation, not current proof
Paths, hashes, commits, process IDs, ports, campaign positions, and repository states stored in continuity are remembered pointers until currentness is reverified when the decision depends on them.

### H12 — RES does not create doctrine
Research understanding can remain powerful and load-bearing as `INFERRED` without becoming governing law. Doctrine Snapshot and Trace Matrix retain their separate jobs.

### H13 — Mutable process can emit immutable observations
A running process may continue changing while a bounded observation/snapshot is sealed. Bind the subject/time boundary rather than falsely requiring global immutability.

`MUTABLE_PROCESS != MUTABLE_PUBLISHED_OBSERVATION`
`CONTINUITY != PROOF`
`RECOVERY_METADATA != AUTHORITY`
`PROTOCOL_DEFAULT_MODE != ACTIVE_MODE_AUTHORITY`
`SUCCESS_PATH_RECOVERY != FAILURE_PATH_RECOVERY`
